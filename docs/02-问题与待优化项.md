### 🆕 2026-08-11 第五轮（audioStreamer 原生音频流播放器集成与兜底完善）

> 本次只改 [html/test_SMS_monitor.html](html/test_SMS_monitor.html)。本轮在第四轮引入 `audioStreamer` 的基础上补全三处关键细节，确保报警循环与锁屏自愈在所有设备上都稳定。

#### 功能实装（3 项 P1）

| 编号 | 等级 | 标题 | 修复方式 |
|------|------|------|----------|
| **F2** | 🟧 P1 | `setLoop` 必须在 `openPlayer` 回调内调用（作用在已打开的实例上） | `startAlarmLoop` / `startTestPlay` 都改为先 `openPlayer`，回调成功后再 `setLoop`；真机验证：调整后原生 `setLoop(true)` 生效（报警 4 分钟内无 `finished` 回调） |
| **F3** | 🟧 P1 | JS 兜底重播（兼容原生 setLoop 失效的设备） | 状态监听器内：`finished + audioLoopEnabled + isPlaying` 时重新 `openPlayer`；带 `JS_REPLAY_MAX = 30` 上限防护，达到上限后强制停止并打 error 日志 |
| **F4** | 🟧 P1 | resume / appactive 自愈 | APP 从后台切回前台时，若 `isPlaying=true` 且 30 秒内无音频状态回调（说明已被系统回收），自动重启警报；30 秒内有回调说明原生循环还在正常跑，跳过自愈避免打断 |

**关键调用顺序（最终实现）**：
```js
// 1. 先 openPlayer 打开播放器（Android 上自动播放，无需 resume）
audioStreamer.openPlayer({ path: audioPath }, function(ret) {
    if (ret.status) {
        // 2. 在回调里再 setLoop（作用在已打开的实例上）
        setAudioLoop(true);
    }
});

// 3. JS 兜底（监听 finished 事件）
audioStreamer.addEventListener({}, function(ret) {
    if (ret.state === 'finished' && audioLoopEnabled && isPlaying) {
        if (__jsReplayCount >= JS_REPLAY_MAX) {
            // 达到上限，强制停止
            isPlaying = false;
            return;
        }
        __jsReplayCount++;
        audioStreamer.openPlayer({ path: replayPath }, ...);  // 重新打开
    }
});
```

**日志标签系统（v3 改进）**：
所有关键节点加 `[标签]` 前缀，方便日志过滤：
- `[startAlarmLoop]` `[startTestPlay]` — 播放入口
- `[openPlayer 回调]` — 播放器是否创建成功
- `[setLoop]` — 循环标志是否生效
- `[JS 兜底重播] 第 N/30 次` — 兜底触发次数（v3 加 30 次上限）
- `[resume 自愈]` `[appactive 自愈]` — 锁屏回前台自愈（v3 加 30 秒防护，循环正常时跳过）

**新增变量**：
- `__jsReplayCount` — JS 兜底累计次数（防止某台设备原生 setLoop 完全失效时无限循环）
- `JS_REPLAY_MAX = 30` — 单次报警最多重播次数（实测 `short_ring.mp3` 单曲 3s，30 次约 90s，足够真机定位问题）
- `__lastAudioStateTime` — 最近一次音频状态回调的时间戳（用于 resume 自愈防护判断）

**注意**：兜底逻辑是兼容性安全网，正常设备上不应触发；如果看到 `[JS 兜底重播]` 日志说明那台机器原生 `setLoop` 不生效，需要真机定位。

### 🆕 2026-08-11 第四轮（audioStreamer 原生音频流播放器）

> 本次只改 [html/test_SMS_monitor.html](html/test_SMS_monitor.html) 和 [config.xml](config.xml)。用户痛点："锁屏时警报铃声 30 秒左右就被掐断，听不到持续警报"。

#### 功能实装（1 项 P0）

| 编号 | 等级 | 标题 | 修复方式 |
|------|------|------|----------|
| **F1** | � P0 | 锁屏/后台 30 秒掐断警报（api.startPlay + JS setTimeout 递归循环失效） | 引入用友 `audioStreamer` 原生音频流播放器，setLoop + openPlayer 由原生维持循环（openPlayer 自动播放）；删除原 `startContinuousPlay` 的 setTimeout 递归；新增 `addEventListener` 监听播放器状态写日志追溯 |

**修复要点**：

| 改造前 | 改造后 |
|------|------|
| `api.startPlay({path})` 配合 JS `setTimeout` 递归 | `audioStreamer.openPlayer({path})` 在回调内 `setLoop({loop:true})`（**调用顺序关键**——setLoop 必须作用在已打开的实例上；openPlayer 自动播放，**Android 上不能调 resume()**——只 iOS 支持，否则抛 `TypeError: audioStreamer.resume is not a function`） |
| 循环由 JS 定时器维持，锁屏后 WebView 暂停 → 30 秒左右停 | 循环由原生播放器维持，依赖前台服务 + `backgroundMode="audio"` 持续播放 |
| 试听/警报混用同一 `api.startPlay` 调用栈 | 独立封装 `startAlarmLoop` / `startTestPlay`，互斥逻辑清晰 |
| 无播放状态可观测（JS 端只看到回调完成） | `audioStreamer.addEventListener` 监听 `prepare/buffering/resume/pause/finished/error` 全部写入日志（与官方文档一致） |
| `pause` 状态中 `api.stopPlay()` 强制停止警报 | **`pause` 不再停止警报**——锁屏/退后台正是要持续播放的场景 |
| `ret.status` 当作"播放完成"回调使用 | `ret.status` 仅表示播放器打开成功；播放完成由 `finished` 状态触发 |

**新增函数（[test_SMS_monitor.html:1165-1420](html/test_SMS_monitor.html#L1165-L1420)）**：

- `describeAudioState(state)` — 状态名 → 中文描述（用于日志）
- `initAudioStreamer()` — 模块初始化（含 null 检查与错误日志）
- `registerAudioStateListener()` — `addEventListener` 状态监听（含 JS 兜底重播 + `__lastAudioStateTime` 记录）
- `setAudioLoop(loopEnabled)` — 设置循环模式（被 `openPlayer` 回调内部调用）
- `startAlarmLoop(audioPath, callback)` — 启动循环警报（`openPlayer` → 回调内 `setLoop(true)`）
- `stopAlarmLoop()` — 停止警报（同时重置 `__jsReplayCount`）
- `startTestPlay(audioPath, callback)` — 启动试听（`openPlayer` → 回调内 `setLoop(false)`，单次）
- `stopTestPlay()` — 停止试听

**修改函数**：
- `playAlert` [test_SMS_monitor.html:1620-1700](html/test_SMS_monitor.html#L1620-L1700)：调用 `startAlarmLoop` 替代 `startContinuousPlay`，`isPlaying = true` 移进 `playSuccess` 回调
- `stopAlert` [test_SMS_monitor.html:2100-2130](html/test_SMS_monitor.html#L2100-L2130)：`api.stopPlay()` → `stopAlarmLoop()`
- `testSound` [test_SMS_monitor.html:2540-2620](html/test_SMS_monitor.html#L2540-L2620)：改用 `startTestPlay` / `stopTestPlay`；单次播放自然完成由监听器自动恢复按钮和音量
- `showAlertDialog` 点击回调：调用 `stopAlarmLoop`，并重置 `__jsReplayCount`
- `pause` 监听器：正式警报不停止，只停止试听
- `resume` / `appactive` 监听器：若 `isPlaying=true` 且 30 秒内无音频状态回调，自动重启警报

**删除**：
- 整个 `startContinuousPlay()` 函数（含 500ms setTimeout 递归循环）

**日志预期输出**（警报场景，已验证 v2/v3 后）：
```
[startAlarmLoop] 准备打开播放器，path=widget://res/short_ring.mp3
[openPlayer 回调] ret={"status":true,"duration":3}
[setLoop] 调用 audioStreamer.setLoop({loop: true})
[setLoop] 设置完成: audioLoopEnabled=true
循环警报播放器已创建并开始: widget://res/short_ring.mp3 (openPlayer=成功, setLoop=成功)

（此后无 finished / resume 回调 → 原生循环持续工作）
```

**注意**：能否真正绕过 30 秒掐断还取决于：
- `config.xml` 已配 `backgroundMode="audio"` + `foregroundService` + `notification` + `wakeLock`（本次确认已齐全）
- 手机厂商系统（小米/华为/OPPO/vivo）的"自启动"和"后台运行"开关需用户手动开启

### B9. ✅ 锁屏 / 后台 30 秒掐断警报（已修复）

📍 旧位置：[html/test_SMS_monitor.html:1499-1532](html/test_SMS_monitor.html#L1499-L1532)（`startContinuousPlay` 函数）

**问题现象**：用户收到匹配短信触发警报后，**锁屏状态下约 30 秒后声音就停了**，用户听不到持续警报；按 Home 键退后台同理。

**根因**：循环播放用 `api.startPlay` + JS 端 `setTimeout` 递归模拟（500ms 间隔），循环依赖 JS 定时器维持。WebView 在锁屏 / 后台会被挂起（WebView 不在前台 / CPU 休眠），`setTimeout` 不再触发 → 播放完成回调不再执行 → 递归停止 → 声音约 30 秒后断。

```js
function startContinuousPlay(audioPath, smsContent) {
    api.startPlay({ path: audioPath }, function(ret, err) {
        if (ret) {
            if (isPlaying) {
                setTimeout(function() {                    // ← 锁屏后不触发
                    if (isPlaying) {
                        startContinuousPlay(audioPath, smsContent);
                    }
                }, 500);
            }
        }
    });
}
```

#### 三方案对比与选型决策

| 维度 | 方案 A：`api.startPlay`（旧） | 方案 B：`liveAudioPlayer` | 方案 C：`audioStreamer` ✅ |
|------|-------------------|----------------------|----------------------|
| **循环机制** | JS 端 `setTimeout` 递归（500ms） | ❌ **不支持循环**（已确认） | ✅ 模块自身支持（`setLoop({loop:true})`） |
| **锁屏 / 后台表现** | ❌ 30 秒左右被掐断（WebView 定时器冻结） | ✅ 由原生播放器维持，理论上能持续 | ✅ 由原生播放器维持，理论上能持续 |
| **依赖基础能力** | 无 | `backgroundMode="audio"` + 前台服务 + 通知权限 | 同左（依赖项当前已齐全） |
| **API 形态** | `api.startPlay({path}, cb)` + `api.stopPlay()` 两条命令 | `player.play({url})` 一条命令（含播放启动语义） | `setLoop` + `openPlayer` 两步走（openPlayer 自动播放；**Android 上不能调 resume()**） |
| **回调语义清晰度** | 回调即"播放完成" | 回调即"播放启动成功"（含义直观） | 回调即"播放器打开成功"，状态机通过 `addEventListener` 独立提供 |
| **状态可观测性** | ❌ 无（只能猜） | 弱 | ✅ 强（`prepare/buffering/resume/pause/finished/error` 全状态写入日志，与官方文档一致） |
| **循环字段文档确定性** | - | 用友版本不支持循环（用户已确认） | 用友官方文档明确 `setLoop({loop:true})`，可在线验证 |
| **音频会话控制（来电暂停）** | ❌ 无 | � 无 | ✅ `onCall()` / `onNormal()` 自动处理来电 / 挂断场景 |
| **进度控制** | ❌ 无 | ❌ 无 | ✅ `seekToTime` / `getCurrentTime` / `getBufferingRatio` |
| **实时进度监听** | ❌ 无 | ❌ 无 | ✅ `addProgressListener` 监听 `progress` 字段 |
| **本项目已有引用** | ✅ 现存 | ❌ 无 | ❌ 无（本次新增） |
| **风险** | 锁屏 30 秒掐断（用户实际反馈问题） | 即使接入也必须配套 JS 端递归循环，等于绕一圈回到方案 A 的痛点 | setLoop 必须在 openPlayer 前调用，顺序错则循环失效；模块需加入自定义 Loader；**Android 误调 resume() 会抛 TypeError** |
| **结论** | 不可用 | 不可用（无循环能力） | **最终选用** |

**选型理由**：

1. **方案 A 直接淘汰**——30 秒掐断是用户真实痛点，JS 端 setTimeout 在 WebView 锁屏后必然冻结。
2. **方案 B 名义上可作"原生播放"备选，但缺循环能力**——用友版本已确认不支持循环，若强行接入就必须**配套 JS 端递归循环**，等于绕一圈回到方案 A 的痛点，没有实际收益。
3. **方案 C 选定的额外收益**（不只是循环）：
   - **来电暂停**：`onCall()` / `onNormal()` 在警报响起期间接到电话可自动暂停，结束自动恢复——短信警报场景尤其重要。
   - **完整状态机**：`addEventListener` 提供 6 种状态（`prepare/buffering/resume/pause/finished/error`），便于日志追溯锁屏/后台播放异常。
   - **进度可查可控**：`seekToTime` / `getCurrentTime` / `getBufferingRatio` + `addProgressListener`，后续如需"已播放 X 秒""缓冲到 80% 才播放"等高级功能可直接用。

两者**都不绕过厂商电池策略**，所以都依赖 config.xml 中已配齐的 `backgroundMode` / `foregroundService` / `notification` / `wakeLock` 四件套。
