### B3. `processSMS` 递归无终止条件 → 栈溢出

📍 [html/test_SMS_monitor.html:648-653](html/test_SMS_monitor.html#L648-L653)

```js
// 并发更新检测：验证期间是否有其他实例修改了数据
var latestStoredRecentSMS = localStorage.getItem('recentSMS');
var latestStoredAlertRecords = api.getPrefs({sync: true, key: 'alertRecords_' + currentYear});
if (latestStoredRecentSMS !== storedRecentSMS || latestStoredAlertRecords !== storedAlertRecords) {
    addLog('检测到并发更新，重新检查重复', 'info');
    return processSMS(sms); // ← 无限递归
}
```

**问题**：当 `localStorage` / `prefs` 在高频并发下持续变化时，会无限递归 → **栈溢出** → APP 崩溃。

**修复**：
```js
// 增加最大重试次数 + 改用 while
const MAX_RETRY = 3;
let retry = 0;
while (retry++ < MAX_RETRY) {
    if (/* 无并发 */) break;
}
```

### B5. 初始关键词删除按钮传参错误

📍 [html/test_SMS_monitor.html:152](html/test_SMS_monitor.html#L152)、[156](html/test_SMS_monitor.html#L156)

```html
<button class="btn btn-small btn-danger btn-delete" onclick="removeKeyword(this)">−</button>
```

但 [html/test_SMS_monitor.html:427](html/test_SMS_monitor.html#L427) 函数定义为：

```js
function removeKeyword(button, index) {
    if (keywords.length <= 1) { ... return; }
    keywords.splice(index, 1);  // ← index 为 undefined → splice(undefined, 1)
    ...
}
```

而新生成的 [html/test_SMS_monitor.html:412](html/test_SMS_monitor.html#L412) 用了正确的双参数调用：

```html
<button ... onclick="removeKeyword(this, ${index})">−</button>
```

**问题**：根据 MDN 规范，`Array.prototype.splice(start)` 当 `start` 为 `undefined` 或无法转为整数时按 **0** 处理。所以 `splice(undefined, 1)` 实际是 `splice(0, 1)`，**总是删除数组第一项**（索引 0），而非最后一项。

行为复现：
- 初始 `keywords = ['湖北交警', '鄂AY366Q']`
- 点第一个按钮 → 删除 `keywords[0]`（湖北交警），剩下 `['鄂AY366Q']`
- 此时 DOM 上显示的"鄂AY366Q"对应的 onclick 仍是旧的 index=1，但实际它在数组里已变成 index=0
- 点第二个按钮（仍是 `removeKeyword(this)`，index=undefined）→ 又从 `keywords[0]` 删除

也就是说：**无论点哪个按钮，被删的总是数组第一项**，而非"当前按钮对应的那一项"。

**修复**：把初始 HTML 也改为 `removeKeyword(this, 0)` / `removeKeyword(this, 1)`，或重构为统一的 `data-index` 绑定方式：

```html
<button ... data-index="${index}" onclick="removeKeyword(this, ${index})">−</button>
```

### B6. `pause` 事件中错误释放互斥锁

📍 [html/test_SMS_monitor.html:281-284](html/test_SMS_monitor.html#L281-L284)

```js
api.addEventListener({ name: 'pause' }, function(ret, err) {
    ...
    // 页面暂停时释放互斥锁
    window.__SMS_MONITOR_LOCK = false;
});
```

**问题**：APICloud 中 frame 切换（如切到统计页）会触发 `pause`，但主框架（main_frame）仍然持有这个锁的引用。释放后，frame 重新显示时不会重新注册监听 → **短信接收不到**。

这与 git log 中 `7021d3a 解决监听到报警短信后重复处理的问题` 的初衷冲突。

**修复**：不要在 `pause` 中无条件释放锁；只在 `viewdisappear`（彻底离开页面）时释放，并配合 frame 生命周期管理。

### B7. XSS 风险 — 短信内容直接拼接 HTML

📍 [html/test_SMS_monitor_statistics.html:2737](html/test_SMS_monitor_statistics.html#L2737)

```js
content += '<div ...>' + record.content + '</div>';
```

📍 [html/test_SMS_monitor_statistics.html:1518](html/test_SMS_monitor_statistics.html#L1518)

```js
`<div ... white-space: pre-wrap; word-break: break-all;">${record.content}</div>`
```

**问题**：短信内容可被攻击者控制（虽然运营商短信网关被劫持罕见，但属于理论风险），包含 `<script>` / `<img onerror>` 等会被执行。

**修复**：
```js
function escapeHtml(s) {
    return s.replace(/[&<>"']/g, c => ({
        '&': '&amp;', '<': '&lt;', '>': '&gt;',
        '"': '&quot;', "'": '&#39;'
    })[c]);
}
content += '<div>' + escapeHtml(record.content) + '</div>';
```

### B8. 跨年保存记录的时间错位

📍 [html/test_SMS_monitor.html:227](html/test_SMS_monitor.html#L227)（脚本加载时计算 currentYear）  
📍 [html/test_SMS_monitor.html:1326](html/test_SMS_monitor.html#L1326)（保存时重新计算 year/month/day）

```js
// 脚本顶部
var currentYear = new Date().getFullYear();

// recordAlert 内
record = {
    year: new Date().getFullYear(),   // ← 保存时刻的年份
    month: new Date().getMonth() + 1,
    ...
};

// 保存到 key
api.setPrefs({ key: 'alertRecords_' + currentYear, ... });  // ← 顶部计算的年份
```

**问题**：**2025-12-31 23:59:59.999 收到短信但到 2026-01-01 才进入 `processSMS`**：
- `record.year` = 2026（短信里的 date 字段也是 2026）
- 但保存 key 是 `'alertRecords_' + currentYear` —— 若 currentYear 在脚本加载时计算（2025），记录就被保存到 2025 年的桶里；
- 统计页 [test_SMS_monitor_statistics.html:786-790](html/test_SMS_monitor_statistics.html#L786-L790) 按 `record.year === currentYear` 过滤 → 这条记录**永远不会被统计**。

**修复**：统一用 `record.timestamp` 推导 key，年份字段只是冗余索引。
